# Oracle loop retro r1 — Claude (goose)
## Summary (≤5 lines)
The loop works: 30/32 issues reached `agent/done`. The two blockers (#1, #66) are process/authority failures, not code failures. The dominant cost is wasted infra rounds — haiku workers crash during finalize after completing work (false AGENT_STRIKEs), deepseek burns cash on rounds that haiku could handle, recipe/lane contradictions deadlock tasks before work begins, and `build_provision_response`'s case-by-case assembly needs parametrized invariant tests to stop review-round whack-a-mole. The ledger itself is too sparse to answer budget/calibration questions quantitatively.
## Findings (ranked, ≤6)
1. **Haiku finalize-phase crashes → false-negative AGENT_STRIKEs** — #43 (strike comment contains green CI output, PR #51 merged), #42 (same: PR #53 merged), #29 round 2 (same: PR #48 opened, CI 97 passed). Workers complete all work, push branches, open green-CI PRs, then crash during summary/stats write. Ledger shows `worker_exits: ["failed"]`, `ci_sequence: [null]` masking real success. The 80→200 turn-cap fix (homelab `8a4a1e1`) doesn't help — the crash is in the verbose JSON output phase, not code work. The coordinator correctly recognized the PRs in #42/#43 (no re-dispatch), but in #29 re-dispatched an identical haiku round that "failed" identically.

2. **Recipe/lane authority contradiction — same deadlock on two issues** — #47 (rank 2) and #66 (rank 18). `.agents/fix.yaml` hard-rule says "Do NOT edit chart/" / "Do NOT edit .github/". `docs/process/TRACKS.md` assigns `chart/**` to `track/deploy` and `.github/workflows/ci.yaml` to `track/chassis`. Workers faithfully refuse (correctly), coordinator blocks rather than violating policy (correctly), but detection is at dispatch time — after queuing. #47 required human amendment to fix.yaml; #66 is currently `agent/blocked` awaiting the same decision. Each occurrence wastes 1+ reconcile ticks + a human escalation cycle.

3. **RT-STATUTE-PROVISION "whack-a-mole" — 3 review rounds on #1 find the same defect class** — #1's `build_provision_response` burned TS rounds 1→2→3 on new instances of the same CITE-invariant violation (partial/duplicated text under §-citation). Each round the reviewer *ran the engine* and found a new code path the prior fix missed: single-lõige wrong prefix → all-points lõige dropped → whole-§ sibling path still duplicates. The spec is prose (RT-STATUTE-PROVISION: "no code path returns law text without its citation"), but the implementation assembles text case-by-case with if/elif chains. Each new lõige shape discovered during review requires a code branch the prose invariant doesn't enumerate.

4. **deepseek-v4-flash = 100% of non-zero costs, no quality advantage** — deepseek on 3 tasks: #1 ($0.248, 4 rounds), #8 ($0.1254, 2 rounds, 53.7h wall), #52 ($0.154, 1 round). Total: $0.5274. All 22 haiku-only tasks: $0.00, 1 round each, all `agent/done`. #1's 4 deepseek rounds delivered a scaffold; haiku delivered equivalent scaffolds in 1 round on #43, #42, #44, #46, #49, etc. deepseek's only use was as fallback after haiku infra strikes — but the quality of its output was not better.

5. **Unflagged `specs/` edits → deterministic review round-trip** — #8 (rank 3): round 1 correct, CI green, but PR body said "No spec changes" while diff touched 3 specs/ files. `.agents/review.md` rule 2 mandates CHANGES_REQUESTED. Round 2 consumed solely to add a "Spec changes:" section to the PR body. #45 (rank 5) shows the related variant: round-2 fix needed because the PR claimed evidence coverage that CI didn't actually produce. The recipe says "list every specs/ change" but the check is prose, not automated — workers forget.

6. **Ledger data collection is pod-lifecycle-coupled → null fields mask trends** — 29/32 tasks have null calibration_error and budget fields. Tasks with known budget estimation at dispatch time (#1: "cap $0.25 / est $0.1633") show null. 24/32 tasks have `wall_time_s: 0`. #1's `worker_exits` is `"0"` (numeric string) vs descriptive `"clean"/"failed"`. AGENT_RUN_STATS post during finalize — when workers crash in that phase (finding 1), the stats are never posted and the coordinator never backfills from PR/review trails. Retro analysis depends entirely on issue-trail narrative vs. structured data.

## Evidence confidence (what you could NOT verify and why)
- **#8's 53.7h wall time**: the ledger shows 193579s but the issue trail shows 2 clean rounds with green CI. I could not determine whether this includes review-queue idle time, pod scheduling delays, or actual work time — the ledger doesn't decompose wall_time into active/idle.
- **Budget estimation vs. actual for haiku tasks**: all haiku tasks show $0.00 cost and null calibration. This could mean accurate estimation (free tier = $0), or it could mean the cost pipeline doesn't track haiku spend. The issue trails don't surface billing records for the haiku tier.
- **retry_storms = 0 for all 32 tasks**: the ledger records zero retry storms, but #1's issue trail describes a "401 User not found auth storm" (dozens of retries of a fatal auth error). This suggests retry_storms tracks harness-level retries (infra) but NOT model-level retry loops within a single worker session — I could not verify the taxonomy boundary.
- **reviewer_rounds = 0 for all 32 tasks**: the ledger shows zero reviewer rounds but the issue trail for #1 shows 4 distinct reviewer verdicts (3 CHANGES_REQUESTED + 1 final). This field may track reviewer *retries due to reviewer infra failure* (vs. reviewer evaluating new worker pushes), but the schema isn't documented in the field notes. All analysis of review round-trips came from issue trails, not the ledger field.
- **Haiku clean-exit tasks (ranks 7-29)**: the ledger shows 1 round, clean exit, CI true for ~22 haiku tasks. I spot-checked 3 (#44, #46, #49) via issue trails and they match, but I did not verify all 22. It's possible some have unreported finalize crashes that the ledger also masks.
