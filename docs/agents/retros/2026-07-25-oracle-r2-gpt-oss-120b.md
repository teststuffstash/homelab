# Oracle loop retro r1 — gpt‑4‑turbo‑preview
## Summary
The ledger and issue‑trail audit reveal that most wasted effort stems from *infra‑level* failures (token‑expiry, pacing, auth‑storm) and *model‑output limits* (truncation), not from pure code‑logic difficulty. A handful of systemic process gaps repeatedly force the loop to burn extra rounds on the same bug family, inflate wall‑time, and trigger budget overruns.

## Findings
| # | Pattern (cross‑task) | Ledger evidence (issue IDs & key fields) | Mechanism (hypothesis) |
|---|----------------------|------------------------------------------|------------------------|
| 1 | **Infra‑token‑expiry / pacing failures** – slow models exceed the 60 min GitHub‑token TTL or hit the 2 h OpenRouter key limit, causing a round to die *without* a worker exit (“0”). | - `oracle‑fleet#1` (rank 1): 4 rounds, 0 reviewer rounds, terminal *blocked*; issue comments show round 1 token‑expiry, round 2 pace‑over‑TTL, round 3 401 auth‑storm. <br>- `oracle‑fleet#66` (rank 18): `agent/blocked` after 1 round, CI “false”. <br>- Multiple “failed” worker exits in ranks 4, 5, 7, 8 (haiku) trace back to the same token‑expiry/pacing guard. | The coordinator → worker key‑mint flow does not guarantee that the model finishes before the token expires. Slow models (e.g. `tencent/hy3:free`, `tencent/hy3`) need > 75 min for scaffold tasks, outlasting the 60 min GitHub token, leading to silent infra deaths and wasted rounds. |
| 2 | **Model‑output truncation (max‑tokens ceiling)** – large monolithic file writes (> 4 k tokens) are cut off, aborting the round. | - `oracle‑fleet#1` round 1 & 3: “goose‑32602‑truncation” after ~15 k char writes (≈ 4 k tokens). <br>- Same pattern repeated on later deepseek attempts (see issue comments). | The egress proxy capped model output at `max_tokens=4096`. When a fix requires writing a > 4 k‑token file in one tool call, the model’s response is truncated, causing an immediate failure irrespective of code quality. |
| 3 | **Repeated “whack‑a‑mole” fixes on the same invariant** – the same `chassis/query.py` bug family (CITE‑invariant violations) is patched in three successive rounds of the same issue. | - `oracle‑fleet#1` rounds 1‑3: 4 fixes in round 1, 2 new fixes in round 2, 2 further fixes in round 3 (all `build_provision_response` related). <br>- Same file edited 7 times across 3 rounds. | Review feedback repeatedly uncovers deeper edge‑cases of the same logical rule, indicating that the spec‑to‑code mapping is under‑specified and static analysis is not catching the invariant before the fix loop starts. |
| 4 | **CI red‑green loops forcing extra rounds** – a CI failure between rounds forces a re‑dispatch even when the worker code is correct. | - `oracle‑fleet#47` (rank 2): `ci_sequence` = [true, false, true]; 3 rounds, 0 reviewer rounds, total cost $0.0469. <br>- No reviewer feedback; the extra round corresponds to the CI “false” entry. | The coordinator proceeds to the next round whenever the CI status is not green, even if the underlying fix was already correct, causing unnecessary round consumption. |
| 5 | **Budget‑cap under‑estimation → 403 key‑limit strikes** – estimated budget too low, actual spend exceeds cap, aborting the round. | - `oracle‑fleet#1` round 3: `worker_exits` = ["failed"]; comment reports “403 Key limit exceeded” after spending $0.5086 vs $0.50 cap. <br>- Similar under‑estimates observed in other scaffold tasks (e.g. rank 6 total $0.154, no cap set). | The budget estimator uses a static token‑price model that does not account for long‑running scaffold builds, leading to a hard‑cap breach and a forced round restart. |
| 6 | **Model‑selection mis‑match for code‑heavy tasks** – low‑capability “haiku” model frequently yields “failed” exits on tasks that need more expressive generation. | - `oracle‑fleet#29` (rank 4) & `oracle‑fleet#45` (rank 5): `rounds` = 2, both workers “failed”. <br>- Both use model `haiku`, which has shown 0 cost but high failure rate on scaffold‑style issues. | The default recipe picks `haiku` for low‑budget tasks, but code‑generation workloads exceed its effective token / reasoning limits, causing silent failures and extra retry rounds. |

## Proposed process changes
| Change | Artifact (exact file/section) | Expected saving* | Confidence |
|--------|------------------------------|------------------|------------|
| A. **Enforce fast‑model default for scaffold tasks** – set `model: openrouter/deepseek/deepseek‑v4‑flash` and `max_duration: 3600s` for any `.agents/fix.yaml` step that creates > 500 LOC. | `.agents/fix.yaml` → add `model: openrouter/deepseek/deepseek‑v4‑flash` under `scaffold:*` and `max_duration: 3600` | Saves ≈ 3 infra rounds per scaffold issue (≈ \$0.05 + ≈ 3 k s wall‑time). | High – directly addresses Findings 1 & 6; already proven by deepseek success. |
| B. **Incremental‑write guardrail** – reject any single `write`/`edit` > 4000 tokens; split large files automatically. | `.agents/fix.yaml` → `rules.inc_write_max_tokens: 4000` (new rule) + CI helper `scripts/guard_incremental_write.sh`. | Prevents 2 truncation failures (Findings 2) → saves ~2 rounds ≈ \$0.07 + ≈ 2000 s. | High – truncation is deterministic; rule enforces known limit. |
| C. **Spec‑lint pre‑flight** – run `scripts/spec-evidence-lint.py` on the target spec before any fix to ensure all invariants (e.g., CITE‑invariant) are fully exercised. | `.agents/fix.yaml` → `pre_flight: scripts/spec-evidence-lint.py --strict`. | Cuts average fix rounds by 1 for invariant‑heavy issues (Finding 3) → ~‑1 round per issue ≈ \$0.04 + ≈ 1500 s across 30 issues. | Medium – depends on completeness of spec lint but already exists; stricter config is low‑cost. |
| D. **CI‑gate bypass on green** – add a “ci‑stable‑window” check that only re‑dispatches on *persistent* CI failures (> 2 min). | `.agents/review.md` → add clause “if CI flickers <120 s, do not start new round”. | Eliminates extra round for transient CI failures (Finding 4) → saves ≈ 1 round per affected issue (≈ \$0.02 + ≈ 800 s). | Medium – simple timing guard; historic CI logs show flickers are short. |
| E. **Budget estimator buffer** – inflate estimated cost by 15 % for any task with `rounds > 1` or `scaffold` flag. | `scripts/budget_estimator.py` → `estimated *= 1.15` when `task.scaffold=True`. | Prevents 403 key‑limit strikes (Finding 5) → saves ≈ 0.5 round per occurrence (≈ \$0.03). | Medium – modest buffer; cost impact negligible vs saved rounds. |
| F. **Model‑selection matrix** – introduce `model_matrix.yaml` mapping task size (`loc_estimate`) to model tier (haiku → deepseek for > 300 LOC). | `model_matrix.yaml` (new file referenced by `.agents/fix.yaml`). | Reduces “failed” exits on haiku tasks (Finding 6) → saves ≈ 1 round per failing issue (≈ \$0.03). | Low‑Medium – needs calibration but clear mapping. |

\*All savings are approximate, derived from ledger averages: 1 round ≈ \$0.03 ± 0.01 and ≈ 1000 s wall‑time.

## Evidence confidence
- **Fully verified:** All ledger rows (cost, rounds, CI sequence, worker exits) and the full comment thread for `oracle‑fleet#1` were inspected; the patterns above are directly observable.
- **Partially verified:** CI flicker timing (Finding 4) and the exact token‑count of large writes (Finding 2) were inferred from comment snippets; a precise measurement would require reproducing the write call.
- **Not verified:** The prevalence of the CITE‑invariant bug across *other* issues (beyond #1) was not exhaustively checked; we assume similar spec gaps exist but lack explicit issue trails.
- **Assumptions:** Model‑speed estimates and budget‑buffer impact are based on observed timings; exact wall‑time may vary per repo state.
