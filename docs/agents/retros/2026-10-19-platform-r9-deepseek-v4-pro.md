# platform loop retro r9 — goose
## Coverage (window, bundle identity, completeness, late corrections)
**Window:** 2026-10-12T00:00:00Z to 2026-10-19T00:00:00Z (Monday 00:00 UTC, exclusive). **Bundle identity:** No retro bundle was provided to this pod; all data drawn from live `gh` reads of issues, PRs, reviews and comments against `teststuffstash/homelab`. **Deep-dive set:** 22 issues created in the window, of which 15 carried `agent-fix` and were dispatched. 14 closed `agent/done`; 1 remains `agent/error` (#2588). 15 agent-authored PRs merged. **Model:** All agent rides used `deepseek/deepseek-v4.1-flash:exacto` (single-rail routing). **Completeness:** The responder ledger, S3 transcripts, and OpenRouter spend data are unreachable from this pod — see Evidence confidence. **Late corrections:** none.

## Summary (≤5 lines)
A batch of 10 simultaneously-filed scan/harness fix issues plus 5 older carry-over tasks formed the agent-fix wave on Oct 14–15, all in the homelab repo (no Goal stacks). 13 of 15 PRs (87%) were APPROVED on first review — the highest recorded throughput. Three cross-task failures hit the single deepseek rail: GitHub pool rate-limit (3 rides on 2 issues, 1 escalated to `agent/error`), prep-brokered App token expiry (2 rides), and `egress-denied` (1 ride, first occurrence). The coordinator filed a fleet ruling (#2601) for the rate-limit class. The second half of the window (Oct 17–18) was dominated by human-led gateway work (FU-270), not agent fixer activity.

## Findings (ranked, ≤6)

**F1 — GitHub pool rate-limit classified as strike, not environment deferral — 3 rides burned, 1 `agent/error` park (№2588, №2562, №2601)**
- **Evidence:** #2588 round 1 rode twice (2026-10-15 20:14Z and 20:20Z), both ending `AGENT_STRIKE: error_class=rate-limit` with zero committed work. The identical-`(model, error_class)` pair triggered the STRIKE-channel terminal → `agent/error` + fleet ruling #2601. #2562 round 1 also struck `rate-limit` (2026-10-14 21:47Z) but pushed a resumable branch and recovered on a later ride. #2412 (in-window closeout) also hit `turn-cap`. The coordinator filed #2601 as a fleet fault ruling: "A GitHub-pool rate limit is an environment deferral, not a strike."
- **Mechanism:** `agent-finalize` matches `rate-limit` (`GraphQL: API rate limit … installation ID`) as `input-unreadable` → AGENT_STRIKE. The launcher's retry ladder sees the `provider: ""` (pool exhaustion, not a model fault) and correctly declines a model swap, but the fall-through parks the issue human-first instead of deferring until the pool's reset window.
- **Process change:** Implement #2601 as specified — in `agents/agent-session.sh` and `agent-runtime/agent-finalize`, on `error_class=rate-limit` (input-unreadable): record the deferral, read the pool reset horizon from `gh api rate_limit --jq .resources`, and return the issue to the dispatch lane once the reset window has passed. Keep the audit comment; drop the human-first park.
- **Expected saving:** Rail 1: €20–30 per avoided out-of-sitting summons (one fleet-level latch avoided per occurrence). Rail 2: ~$0.01–0.03 per avoided strike re-ride. Rail 3: avoids coordinator fleet-ruling rides. At 3 occurrences/wk, ≈€60–90/wk Rail 1 exposure.

**F2 — Prep-brokered App token expires mid-ride with no refresh path — 2 rides lost verification time (№2576, №2178)**
- **Evidence:** #2576's closeout comment (2026-10-14 23:08Z) reports `TOOL_GAP: gh (GH_TOKEN) — the pod's prep-brokered App token expired mid-ride with no refresh path (GH_TOKEN_FILE=/var/run/coordinator-git/GH_TOKEN does not exist in platform-agents), so every verification read 401'd until it was re-fetched by hand … ~5 min of this ride's verification was lost`. #2178's agent-summary (2026-10-14 20:59Z) reports the same TOOL_GAP: `the prep-brokered coordinator token expires mid-ride with no in-pod refresh … every gh call 401'd`. Both rides produced durable work (PRs merged) but verification was blind to the 401 gap.
- **Mechanism:** The coordinator's prep-brokered App token (`GH_TOKEN_FILE`) has a fixed ~1h lifetime. When a ride runs longer than the remaining token life (or when the token is near expiry at dispatch), every `gh` read in the latter half of the ride silently returns 401. The agent cannot distinguish "resource doesn't exist" from "token expired" because 401 on a `gh issue view` returns an empty body. This class is known — #1370 (filed 2026-09-04) already documents the same root cause ("coordinator-git … GH_TOKEN 401s mid-session") but remains open.
- **Process change:** In `agents/agent-session.sh`: add a token-liveness probe before the verification-read block — `gh auth status` or a lightweight `gh api /user`. If it returns non-zero, call the egress proxy's `/loop-git-token` endpoint (already referenced in #2576's TOOL_GAP comment) to refresh the token. The endpoint exists; the code path to consume it from a worker pod does not. Related work: #1370.
- **Expected saving:** Rail 2: ~5 min of wasted model context per expiry event (~$0.01–0.02). Rail 3: avoids verification-blind rides where the agent cannot confirm PR state. Two occurrences observed in this window; frequency is 1–2/wk. Rail 1: zero (auto-handled once the refresh path exists).

**F3 — `egress-denied` strike on #2577 — first occurrence of this class in the platform loop, confirming r7 F5 is still needed**
- **Evidence:** #2577 round 1 struck `AGENT_STRIKE: error_class=egress-denied` (2026-10-14 22:16Z). The agent could not reach external resources to compute `merge-base` for the lock-intake-lint predicate. The coordinator steered the re-ride (22:19Z): "skip the reconnaissance; the coordinator verified the CI arm in-pod … the fix must be expressed as a locally-computable equivalent." The re-ride succeeded and PR #2583 merged. This is the first `egress-denied` strike observed in a platform-loop ride (r7 F5 was filed against oracle-fleet, not homelab). The outcome was correct — the strike was not misfiled, the coordinator steered correctly, and the re-ride landed — but the class still has no automatic recovery.
- **Mechanism:** Worker pods run in namespaces with restricted egress. When the agent attempts a `gh api` call that reaches outside the pod's allowed network path (e.g., computing a cross-repo merge-base), the call fails with a network-level denial. The strike classifier correctly identifies it as `egress-denied` (not a model fault), so no swap is attempted. But the ride terminates with zero committed work — the human operator (or coordinator, in this case) must manually steer the re-ride.
- **Process change:** Already specified by r7 F5: add `egress-denied` to the strike-classifier with an auto-steer rule: if the `Touches:` footprint is computable from local git operations alone (all paths in the same repo), re-ride with an instruction to use `git merge-base` locally instead of `gh api`. This is the exact resolution the coordinator applied manually. Related work: r7 F5 (agent-runtime#164, open).
- **Expected saving:** Rail 1: avoids one in-sitting touch per occurrence (€3–8) or a full E if outside a sitting. Rail 2: avoids one wasted model invocation per strike (~$0.03–0.06). Rail 3: avoids one coordinator steer ride. Frequency: 1 in this window, unknown recurrence.

**F4 — Single-rail routing with no fallback rail: all 6 strike events in the window hit the same model (deepseek-v4.1-flash:exacto)**
- **Evidence:** 15 deep-dive tasks, all annotated `deepseek/deepseek-v4.1-flash:exacto`. Strike classes observed: `rate-limit` (3 occurrences: #2588×2, #2562), `egress-denied` (1: #2577), `turn-cap` (1: #2412), plus output-token-limit co-occurrence on #2562. Zero tasks used any secondary model. The router's per-session pin selects the same model every time — there is no fallback rail. r8 F3 reported the same pattern; Goal #1640 (router-first) is still in assembly.
- **Mechanism:** Same as r8 F3. The launcher's strike→swap ladder requires `provider: <non-empty>` to nominate an alternative; when the error_class is environmental (rate-limit, egress-denied) or the provider field is empty (pool exhaustion), no swap fires. The strike falls through to the coordinator, who has no alternative model to route to either.
- **Process change:** Same as r8 F3 with the refinement from #2601: when the session's model has a live strike record, `/route` should nominate the next-cheapest model below the tier cap. For `rate-limit` specifically, the fix is different (F1 above: deferral, not swap) — no model swap helps when the GitHub pool is the bottleneck. For `egress-denied`, a model swap is also irrelevant (the restriction is network-level). This finding is kept separate to track the class, not to propose a duplicate fix.
- **Expected saving:** No net new saving beyond F1 and r8 F3. This finding records the structural constraint; the fix for the actionable half (provider-axis strikes) is r8 F3, and the fix for the rate-limit half is F1 above.

**F5 — All 15 agent-fix PRs landed with 87% first-review approval — a calibrated review reflex and small-scope task shape**
- **Evidence:** 13 of 15 agent PRs APPROVED on first review. Review details: #2593 DISMISSED (scope issue — touched 2 manifests beyond the 1 CI gate; agent reduced scope same round, re-reviewed APPROVED). #2579 CHANGES_REQUESTED (comment inaccuracy in the tofu `ignore_changes` description; agent fixed in round 2, APPROVED). All other 13 PRs: single APPROVED from `homelab-reviewer`. Contrast: r8 had 44 CHANGES_REQUESTED verdicts (17 on vacuous pins alone) from a 31-task wave. The r7 F1 fix (post-approval BEHIND idle → ≤0.9h) deployed in r8 continues to hold — no agent PR in r9 spent >1h between approval and human merge (the operator reviewed all 15 PRs in one corpus session on Oct 15).
- **Mechanism:** The r9 tasks were homelab-repo fixes (no Goal stacked bases), so the pin-vacuity gate that caused r8's 17 false-positive verdicts was never triggered. The reviewer reflex's scope check (2 of 15 flagged) is correctly calibrated: it catches real scope drift without false positives. The task shape (one fix, one file, one replay row) is the natural unit for homelab-scope work.
- **Process change:** Codify in `.agents/fix.yaml` recipe: the "small-scope, single-file-touch" task shape as a proven pattern. Specifically: one changed source file, one replay row red on base, zero manifest/template changes (those are `build` lane). This is not a new rule — it's documenting what already works, so future task authors (coordinator decompositions) can target it explicitly.
- **Expected saving:** No direct saving (this is a positive finding, not a defect). Indirect: prevents regression by documenting the shape that achieves 87% first-round throughput.

## Task granularity (per deep-dive task: chunked-right / should-have-been-one / fan-out — evidence)

The deep-dive set of 15 agent-fix tasks was correctly chunked. Each task was a single predicate, guard, or lint fix in the homelab repo, independently verifiable with one replay row red on base. Evidence: 13 of 15 (87%) completed in 1 round with no rework or cross-task friction. The only rework was intra-task: #2579's tofu comment inaccuracy (fixed round 2) and #2593's scope overshoot (same round fix). The batch filing of 10 issues on Oct 14 20:04–21:19 caused 2 WIP cap deferrals (#2412 deferred 2×, #2576 deferred 1×), but these cleared within 30 minutes as the first workers completed and released slots — no task was delayed >1h by sibling contention. This contrasts with r8's 39% deferral rate from phantom-pod WIP saturation; the r9 deferrals were genuine slot exhaustion from concurrent real work, which the batch naturally cleared.

**Exception — #2577 (lock-intake-lint fourth site): should-have-been-one with #2412.** The #2412 fix (pin-only/governance/iac-sentinel three-dot cover) and the #2577 fix (lock-intake-lint, same predicate at a fourth site) were filed as separate issues and dispatched separately. The #2577 issue body itself identifies it as "the specific half PR #2578 (#2412) deliberately left unshipped: the FOURTH site." The separation was intentional (different lanes: #2412 touched scripts for 3 gates, #2577 touched 1 script for 1 additional gate), and both merged cleanly. One larger-model task could have covered all 4 sites at once, but the separation caused no friction: 0 cross-chunk rounds, 0 merge conflicts.

**Exception — #2588 (updater master-red): not chunked at all — struck before any work began.** The issue was complete and ready, but 2 rate-limit strikes consumed both rides with zero committed work. This is an infrastructure failure, not a granularity problem.
