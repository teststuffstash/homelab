# platform loop retro r4 — goose (claude-sonnet-4)

## Summary (≤5 lines)
40-task ledger: 19 blocked (48%), 21 merged. deepseek-v4-flash is the dominant failure source (28 of 54 non-clean exits), with context truncation (goose-32602, 9×) and repetition-loops (5×) as the top classes. haiku CI-red loops (6×) and untracked subscription spend mask review-burn costs. Budget calibration errors on sm-tier tasks (homelab#1041: +104.9% overshoot with all-clean rounds) force operator arbitration. Auth-storm clusters on oracle-fleet waste days of wall time (303,790s / 3.5d for #279). Two repos (sleep-tracking, oracle-fleet) are unreachable via fleet token — deep-dive analysis of ranks 2, 4, 6, 7 is ledger-only.

## Findings (ranked, ≤6)

### F1: deepseek-v4-flash context truncation is the #1 first-attempt killer (9 events across 4 stacks)
- **Evidence**: goose-32602-truncation on homelab#778, homelab#791, homelab#1205, circles#32, circles#19, oracle-fleet#272, oracle-fleet#397 (2×), sleep-tracking#123 (2×: xiaomi/mimo-v2.5 + deepseek-v4-flash-0731). The error appears exclusively on round 1, always forces a model swap to haiku, and never self-recovers within the same model. sleep-tracking#123: 2/6 rounds killed by truncation → 12.6 day wall. homelab#1205: truncation at round 1, 6 subsequent haiku rounds + 6 reviewer rounds.
- **Mechanism**: `estimate_budget.py` uses `DEFAULT_CONTEXT_TOKENS = 20_000` but deepseek-v4-flash's effective context window under the Goose harness is smaller (~16K usable before truncation), especially with coordinator brief + repo context loaded. The estimator sizes for 20K tokens but the session overruns, hits the harness limit, and dies before producing output.
- **Process change**: In `agents/estimate_budget.py`, add a model-specific `MODEL_CONTEXT_LIMITS` dict that sets deepseek-v4-flash at 16,384 tokens (override the 20,000 default), so the estimator sizes the cap for a session that fits within the model's usable window, or selects haiku as first-choice for context-heavy issues.
- **Expected saving**: API: ~$0.45 (9 wasted round-1 deepseek rides × ~$0.05). Subscription draw: 9 avoided haiku fallback rounds (amortized ~$0.09; API-equivalent ~$0.18). Operator time: ~€20-30 per blocked task from truncation cascade (sleep-tracking#123 is the clearest case — 12.6d wall, terminal block); conservatively €20-30 for the one out-of-sitting block attributable to this class. **Total: ~$0.72 API + subscription + €20-30 operator.**

### F2: haiku CI-red loops consume reviewer capacity without converging
- **Evidence**: 6 ci-red exits on haiku vs 2 on deepseek-v4-flash. homelab#913: 8 rounds, CI-red at round 4, 14 total reviews, 7 CHANGES_REQUESTED verdicts, escalating to operator codeowner gate and arbitration park. homelab#1205: ci-failed rounds 2-3, 6 reviewer rounds. homelab#379: ci-failed round 4, 4 reviewer rounds. The pattern: haiku produces syntactically valid code that passes worker-side tests but fails CI semantics (merge-path-lint, clause-replays, fixture agreements). The reviewer catches some but not all; CI surfaces the rest, and each cycle costs a reviewer ride.
- **Mechanism**: haiku's smaller model produces changes that satisfy the issue text but miss cross-file invariants enforced by CI linting rules (fixture agreement, families.tsv consistency, transition pins). The reviewer's rubric (§In-diff findings BLOCK) forces CHANGES_REQUESTED for fixable defects, creating a ping-pong where the worker fixes one finding and the reviewer finds another adjacent defect in the same diff — review surface expansion, not worker regression.
- **Process change**: In `agents/coordinator-scan.sh`, add a per-model CI-fail-rate counter that triggers a model-upgrade signal: when haiku accumulates ≥2 CI-red rounds on a single issue, the next dispatch uses deepseek-v4-flash instead (or routes to `agent/arbitrate` early). This implements the existing `AGENT_STRIKE` logic for `ci-red` on haiku specifically.
- **Expected saving**: Subscription draw: ~6 avoided haiku reviewer rides per blocked CI-red loop (amortized ~$0.06; API-equivalent ~$0.12). Operator time: homelab#913 escalated to codeowner → out-of-sitting summons (~€20-30). homelab#1205 and #379 converged without operator but at reviewer cost. **Total: ~$0.18 subscription + €20-30 operator per escalation avoided.**

### F3: sm-tier budget caps terminate all-clean, correct work (calibration overshoot)
- **Evidence**: homelab#1041: 5 rounds all clean, all CI green, calibration_error=1.049, cost $0.5245 vs cap $0.50. The task was producing correct, reviewer-accepted work every round but hit the OpenRouter 403 key limit. Operator had to apply the final fix (f776ebc3) by hand. homelab#778: budget-403 on round 4 (poolside/laguna-s-2.1:free → budget-exhausted), blocking a task later closed as residue. The r3 F5 headroom change (1.5→2.0) was merged but sm-tier with calibration_error >1.0 still overshoots because the headroom multiplies the *estimate*, not the calibration error — an already-wrong estimate stays wrong.
- **Mechanism**: `estimate_budget.py`'s `DEFAULT_CONTEXT_TOKENS=20_000` and `DEFAULT_ROUNDS=3` produce a point estimate that, even with 2.0× headroom, can land in sm when the actual task needs 5+ rounds of deepseek-v4-flash work. The calibration_error field measures post-hoc overshoot but isn't fed back into the estimator — each mis-sized task is a fresh lottery.
- **Process change**: In `agents/estimate_budget.py`, add a `calibration_feedback` path: when an issue's `calibration_error > 1.0` and all rounds are clean+CI-green, auto-escalate the budget tier by one band (sm→md) for the next dispatch on that issue, rather than parking it as `agent/blocked`. The coordinator's `budget-exhausted` clause in `coordinator-scan.sh` already has the tier-escalation table — trigger it on clean-CI + overshoot, not just on the cap hit.
- **Expected saving**: API: $0.03 (the $0.0245 overshoot on #1041). Operator time: €20-30 per arbitration avoided (the operator-sitting to apply the fix by hand). This class affects ~2 tasks in the ledger (homelab#1041, homelab#778). **Total: ~$0.06 API + €40-60 operator.**

### F4: repetition-loop strike rule never fires — 5 identical strikes waste all rounds
- **Evidence**: oracle-fleet#304: 5 consecutive round-1 deepseek-v4-flash harness-death exits, all error_class=repetition-loop, all identical (model, error_class) pair. The ledger shows 0 retry_storms and 0 reviewer_rounds — the loop persisted until the harness itself aborted after 5 rounds without ever escalating to `agent/error`. Active time: 13,165s, wall: 20,933s (~5.8h), cost: $0.00 tracked (unreachable to verify). No PR was ever created.
- **Mechanism**: The coordinator-scan.sh strike counter (§State machine: "a second strike with the identical (model, error_class) pair on one issue is not a swap — it routes to the `agent/error` STRIKE-channel path") does not recognize `repetition-loop` as a strike-triggering error_class. The harness correctly dies, but the re-dispatch loop keeps selecting the same model with the same parameters, producing the same result. The strike counter sees these as harness-level retries, not strikes, because `retry_storms=0` in the ledger.
- **Process change**: In `agents/coordinator-scan.sh`, add `repetition-loop` to the strike-triggering error_class set. When the count reaches 2 for the same (model, error_class) on one issue, route to `agent/error` with machine-readable marker, per the existing STRIKE-channel path. This is a one-line list addition, not a new mechanism.
- **Expected saving**: API: ~$0.15 (3 wasted deepseek rides after the 2-strike threshold). Wall time: ~12,000s recovered (the 3 post-threshold rounds). No operator time saved (already self-terminating at round cap), but the task would reach `agent/error` in 2 rounds instead of 5. **Total: ~$0.15 API + 3.3h wall time.**

### F5: auth-storm clusters indicate OpenRouterKey provisioning race (oracle-fleet only)
- **Evidence**: oracle-fleet#279: 3 auth-storms (deepseek-v4-flash, http-401-storm), 303,790s wall (3.5 days), 1,502s active. oracle-fleet#273: 2 auth-storms, 5,561s wall. oracle-fleet#272: 1 auth-storm, 30,190s wall. All oracle-fleet, all deepseek-v4-flash, all auth-storm on round 1. The storms cluster temporally (Aug 26-30) and by stack (oracle-fleet exclusively), suggesting an infra-level trigger rather than per-task causes. The retry_storms counter recorded 3, 2, 1 respectively — the harness is retrying, but each retry hits the same 401.
- **Mechanism**: The ephemeral OpenRouterKey broker provisions keys just before dispatch, but the key is not immediately valid across OpenRouter's provider routing layer. The first few requests using the new key get 401 responses until propagation completes (~seconds to minutes). The harness retries immediately with the same key, burning API attempts and wall time without a readiness check.
- **Process change**: In the harness (referenced as `agent-session.sh`'s launcher path, not excerpted), add a pre-flight key readiness probe before the first model call: a minimal (1-token) OpenRouter `/api/v1/models` GET with the new key, retried at 5s intervals up to 60s, failing the round with a distinct `key-not-ready` error_class (counts as infra, not a logic round) if it never succeeds. This is a new error_class, so add it to the strike-triggering set as well.
- **Expected saving**: API: ~$0.06 (3+2+1 = 6 wasted deepseek auth-storm rides × ~$0.01 each — auth failures are token-light). Wall time: oracle-fleet#279 wall drops from 303,790s to ~1,500s (active time). The oracle-fleet constraint means this class affects one stack. **Total: ~$0.06 API + ~3.5d wall time recovered (one task).**

### F6: untracked haiku/subscription costs mask real platform spend on 20+ tasks
- **Evidence**: 20 tasks with total_cost_usd=0.00 but substantial haiku round counts: homelab#913 (7 haiku rounds, $0.00), homelab#625 (4 haiku rounds, $0.00), homelab#1205 (6 haiku rounds, $0.00), homelab#1151 (5 haiku rounds, $0.00), homelab#1268 (6 haiku rounds, $0.00), homelab#1529 (5 haiku rounds, $0.00), homelab#1539 (5 haiku rounds, $0.00), and 13 more. The ledger blind-spot note confirms: "$0.00 on subscription/haiku rows means UNTRACKED, not free." The Go meter computes API-equivalent pricing natively per the brief, but per-task cost attribution is absent because the subscription rail bills monthly, not per-token.
- **Mechanism**: haiku runs on a subscription rail (likely OpenCode/AI or similar flat-fee plan). The coordinator's per-session OpenRouterKey cap mechanism only gates paid-API (OpenRouter) spend — subscription rides have no per-task cap, so the estimator doesn't even try. But the *value* consumed matters for platform economics: F2 above shows haiku's CI-red loops cost real reviewer time, and without per-task cost data, those loops are invisible to the cost model.
- **Process change**: In the harness (not excerpted, but referenced in the coordinator brief as "stats posted, HEAD unmoved"), add haiku token counting to `AGENT_RUN_STATS`: capture `usage.prompt_tokens` and `usage.completion_tokens` from the model response (available in all major LLM APIs), emit them in the stats comment, and compute an API-equivalent $ figure using the Go meter's list-price conversion. This is a measurement change, not a gating change — no dispatch behavior is altered.
- **Expected saving**: Audit visibility only — no direct € or $ savings. Enables future findings to quantify haiku spend and justify model-selection changes. Note: this finding's only saving is rail 3 (subscription draw visibility), which is the cheapest rail. Filed to clear the blind spot for r5+.
